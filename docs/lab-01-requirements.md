# Требования к проекту — Лабораторная работа №1

## 1. Название проекта

**Информационная система бронирования аудиторий преподавателями университета**

## 2. Основной объект

Основная сущность системы — **бронь аудитории**.

Для каждой брони используются:

* машинный идентификатор `id`;
* человекочитаемый номер `number`;
* название/назначение `title`;
* идентификатор аудитории `auditoriumId`;
* описание `description`.

Справочник системы — **Аудитории**.

Связь брони с аудиторией выполняется через числовое поле `auditoriumId`.

## 3. Роли

| Роль                       | Права                                                   |
| -------------------------- | ------------------------------------------------------- |
| Преподаватель              | Создаёт бронь аудитории                                 |
| Диспетчер расписания       | Назначает ответственного исполнителя                    |
| Ответственный за аудитории | Обрабатывает назначенную ему бронь и изменяет её статус |

Роли имеют разные права. Создатель брони и исполнитель являются разными ролями.

## 4. Статусы

В системе используются ровно четыре статусных кода:

| Код          | Значение                        |
| ------------ | ------------------------------- |
| `New`        | Бронь только создана            |
| `InProgress` | Исполнитель взял бронь в работу |
| `Closed`     | Обработка брони завершена       |
| `Cancelled`  | Бронь отменена                  |

## 5. Процесс

Основной процесс:

**Преподаватель создаёт бронь → Диспетчер расписания назначает ответственного → Ответственный принимает бронь в работу → Бронь обрабатывается → Бронь закрывается или отменяется.**

Назначение исполнителя и изменение статуса являются **разными действиями**.

## 6. Функциональные требования

### FR-01. Создание брони

**Роль:** Преподаватель.

Преподаватель должен иметь возможность создать бронь, указав название, аудиторию и описание.

**Результат:** новая бронь создаётся с уникальными `id` и `number` и получает статус `New`.

### FR-02. Выбор аудитории

**Роль:** Преподаватель.

При создании брони преподаватель должен выбрать аудиторию из справочника.

**Результат:** в брони сохраняется числовой идентификатор `auditoriumId`.

### FR-03. Просмотр списка броней

**Роль:** Авторизованный пользователь.

Пользователь должен иметь возможность просматривать список существующих броней.

**Результат:** отображается список броней с номером, названием, аудиторией и статусом.

### FR-04. Просмотр информации о брони

**Роль:** Авторизованный пользователь.

Пользователь должен иметь возможность просматривать данные конкретной брони.

**Результат:** отображаются основные сведения о выбранной брони и её текущий статус.

### FR-05. Назначение исполнителя

**Роль:** Диспетчер расписания.

Диспетчер должен иметь возможность назначить ответственного за обработку конкретной брони.

**Результат:** в брони фиксируется назначенный исполнитель.

### FR-06. Приём назначенной брони в работу

**Роль:** Ответственный за аудитории.

Ответственный должен иметь возможность принять назначенную ему бронь в работу.

**Результат:** статус брони изменяется с `New` на `InProgress`.

### FR-07. Завершение обработки

**Роль:** Ответственный за аудитории.

Ответственный должен иметь возможность завершить обработку назначенной ему брони.

**Результат:** статус изменяется на `Closed`.

### FR-08. Отмена брони

**Роль:** Ответственный за аудитории.

Ответственный должен иметь возможность отменить обрабатываемую бронь.

**Результат:** статус изменяется на `Cancelled`.

### FR-09. Ограничение изменения статуса

**Роль:** Ответственный за аудитории.

Ответственный может изменять статус только тех броней, которые назначены ему.

**Результат:** попытка изменения чужой брони запрещается.

### FR-10. Разделение прав ролей

Система должна ограничивать действия пользователей в соответствии с их ролями.

**Результат:** преподаватель не может назначать исполнителя, диспетчер не может создавать бронь от имени преподавателя, а ответственный не может назначать исполнителей.

## 7. Нефункциональные требования

### NFR-01. Сохранность данных

Данные созданных броней должны сохраняться в PostgreSQL и оставаться доступными после перезапуска серверного приложения.

**Проверка:** создать бронь, перезапустить сервер, снова открыть список броней и убедиться, что созданная запись сохранилась.

### NFR-02. Авторизация

Доступ к функциям системы должен предоставляться в соответствии с ролью авторизованного пользователя.

**Проверка:** войти под разными ролями и проверить доступность разрешённых и запрещённых действий.

### NFR-03. Целостность данных

Каждая бронь должна иметь уникальные `id` и `number`, а `auditoriumId` должен ссылаться на существующую аудиторию.

**Проверка:** попытаться создать некорректную ссылку на аудиторию и проверить отказ операции.

### NFR-04. Разделение компонентов

Система должна состоять из клиентской части на Vue 3, серверной части на ASP.NET Core и базы данных PostgreSQL.

## 8. Use Case

### UC-01. Создание и назначение брони

**Акторы:** Преподаватель, Диспетчер расписания.

**Предусловие:** пользователь авторизован в системе с соответствующей ролью.

**Основной поток:**

1. Преподаватель открывает форму создания брони.
2. Указывает название бронирования.
3. Выбирает аудиторию из справочника.
4. Вводит описание.
5. Подтверждает создание.
6. Система создаёт бронь.
7. Бронь получает статус `New`.
8. Диспетчер расписания открывает список броней.
9. Диспетчер выбирает созданную бронь.
10. Диспетчер назначает ответственного исполнителя.
11. Система сохраняет назначение.

**Альтернативный поток:**

Если указанная аудитория недоступна для выбранного времени, система должна отклонить создание брони и сообщить пользователю о невозможности бронирования.

**Постусловие:** бронь существует в системе в статусе `New` и имеет назначенного ответственного исполнителя.

## 9. Критерии приёмки

### AC-01. Создание брони

**Дано:** преподаватель авторизован в системе и имеет права на создание брони.

**Когда:** преподаватель указывает название, выбирает аудиторию, вводит описание и создаёт бронь.

**Тогда:** система создаёт новую бронь с уникальными `id` и `number`, связывает её с выбранной аудиторией и устанавливает статус `New`.

### AC-02. Назначение исполнителя

**Дано:** бронь существует в системе и имеет статус `New`.

**Когда:** диспетчер расписания назначает ответственного исполнителя.

**Тогда:** система сохраняет назначенного исполнителя для выбранной брони.

### AC-03. Исполнитель переводит бронь в работу

**Дано:** бронь находится в статусе `New` и назначена конкретному ответственному исполнителю.

**Когда:** назначенный исполнитель переводит бронь в работу.

**Тогда:** система изменяет статус брони с `New` на `InProgress`. Пользователь, которому бронь не назначена, не может выполнить это действие.

## 10. Как есть

В текущем процессе информация о бронировании аудиторий может храниться в разных источниках. Преподавателю может быть сложно быстро определить, свободна ли нужная аудитория. Ответственному сотруднику приходится получать информацию о заявках и назначениях отдельно. История обработки брони может быть недостаточно прозрачной. Не всегда очевидно, кто отвечает за конкретную заявку. При использовании разрозненных источников повышается риск потери информации. Также возможны пересечения бронирований одной аудитории. Сотрудникам приходится дополнительно проверять актуальность сведений. Отсутствие единой записи усложняет контроль текущего состояния бронирования. Информация о текущем состоянии бронирования не всегда доступна участникам процесса в одном месте.


## 11. Как будет

После внедрения системы каждая бронь аудитории представлена одной записью. В записи хранятся её номер, название, выбранная аудитория, описание и текущий статус. Преподаватель создаёт бронь через систему. Диспетчер расписания назначает ответственного исполнителя отдельным действием. Назначенный ответственный переводит бронь в работу. Система фиксирует изменения статуса. Пользователи видят актуальное состояние брони в едином списке. Права доступа определяются ролью пользователя. В результате информация о бронировании хранится в единой системе и доступна участникам процесса в соответствии с их правами.

## 14. Критерии готовности лабораторной работы №1

Лабораторная работа считается готовой, если:

* тема проекта определена;
* основная сущность определена;
* справочник и числовая связь определены;
* определены минимум две роли с различными правами;
* назначение исполнителя отделено от изменения статуса;
* определены четыре статуса `New`, `InProgress`, `Closed`, `Cancelled`;
* определены машинный `id` и человекочитаемый `number`;
* определены поля создания;
* описаны функциональные и нефункциональные требования;
* приведён минимум один полный Use Case;
* приведены три критерия приёмки в формате Given/When/Then;
* определены границы семестрового проекта.

## 15. Вопросы к защите

### Граница проекта

В семестровый проект входит основной процесс бронирования: создание брони, назначение ответственного и обработка заявки. Интеграции и расширенные возможности относятся к дальнейшему развитию.

### Проверка нефункционального требования

Для проверки сохранности данных создаётся бронь, после чего сервер перезапускается. После повторного запуска системы необходимо проверить наличие ранее созданной брони.

### Отличие от аналогичных проектов

Отличительной особенностью проекта является процесс бронирования аудиторий преподавателями с разделением ролей: преподаватель создаёт бронь, диспетчер расписания назначает ответственного, а ответственный за аудитории обрабатывает назначенную ему бронь.
